# 游戏项目六步制作主线：现有能力与缺口映射

状态：实施基线 v1  
适用范围：Agent Hub 通用能力之上的游戏制作与运行  
产品原则：**先建游戏，再配置规则、人物、事件与视听内容；“游戏包”只在发布时由系统自动生成，不是策划的制作入口。**

## 一、产品对象与主流程

策划始终操作一个“游戏项目”：

```text
新建游戏
  → 规则与世界状态
  → Agent / NPC
  → 事件与推进
  → 场景与视听
  → 试玩
  → 发布
  → 系统生成不可修改的游戏版本
```

对象边界：

- **游戏项目**：可持续编辑的工作区，保存草稿和引用关系。
- **Agent / NPC**：项目引用 Agent Hub 中已有 Agent；编辑期不复制 Agent。
- **美术与音频资源**：上传到统一资源库，再由场景和事件按稳定编号引用。
- **试玩局**：使用当前草稿创建的隔离测试局，不影响已发布版本。
- **已发布版本**：发布瞬间冻结规则、人物映射、事件和资源版本；运行中的局始终锁定该版本。
- **游戏包**：已发布版本的内部交付形式。由系统生成、校验和安装，普通策划不直接上传或编辑。

## 二、前序能力结论

### 已经具备，可直接复用

| 已有能力 | 游戏侧用途 |
|---|---|
| H0 扩展边界 | 游戏规则不写进 Agent Hub 核心 |
| H1 Run 与版本化状态 | 试玩局、正式局、状态隔离、修改历史 |
| H2 事件、工具结果与提示词合成 | 状态变化留痕、规则结果进入人物上下文 |
| H3 多跳协作 | NPC 咨询、委派、回报和链路审计 |
| H4 群组、频道、会话房间 | 董事会、派系、公开频道和群体会话 |
| H5 工作流、审批和投票 | 董事会表决、审批、会签和超时升级 |
| H6 动态人物能力 | 情绪、认知、主观记忆和动态关系 |
| H7 扩展管理 | 通用扩展的权限、版本、运维与租户隔离 |
| M0 规则注册骨架 | 已证明状态项、动作和结果可以由外部规则声明 |

### 目前尚未具备

M0 只有开发验收用的规则样例和已发布包注册表，**还没有游戏项目、策划编辑流程、正式回合、事件触发、NPC 项目映射、资源库和发布快照**。这些是六步主线要补的内容。

## 三、六步实施映射

## 1. 新建游戏

### 产品功能

填写游戏名称、简介、题材、玩法目标；创建一个可编辑项目。首页显示六步完成度、最近试玩和最近发布版本。

### 可复用能力

- 租户、用户、权限和审计；
- H1 Run 可在后续承载试玩局；
- H7 的扩展版本与租户隔离原则。

### 需要新增

- `GameProject`：名称、简介、题材、玩法目标、草稿状态、负责人；
- 项目成员与编辑/试玩/发布权限；
- 项目概览页和六步导航；
- 草稿修订号，防止多人编辑相互覆盖。

### 借鉴但不照搬

- 借 GDevelop 的 Project Manager 和 Preview 工作流；
- 借 AgentWorld 的 Scenario 声明思想，但项目不是一次运行场景；
- 不引入 GDevelop 的对象、物理、导出平台和完整编辑器。

### MVP 不做

- 项目模板市场、多人实时协同编辑、分支合并；
- 游戏商业化配置、商店、成就和排行榜。

### PM 验收

在页面新建“Speeding 小样”，填写四项信息；返回列表后可再次进入，内容不丢失；另一租户不可查看或修改。

## 2. 规则与世界状态

### 产品功能

策划用中文表单定义核心数值、初始值、上下限，以及玩家行动怎样改变数值。页面使用“状态项、行动、条件、结果”等产品语言，不向普通用户展示 Schema、Manifest 或内部事件编号。

### 可复用能力

- H1 的版本化状态、修改历史、并发保护和冻结；
- H2 的工具结果、幂等提交和不可绕过的状态写入；
- M0 已有状态项、行动、结果和事件注册骨架。

### 需要新增

- 项目级状态项草稿；
- 行动定义：谁能做、需要什么输入、前置条件、产生什么结果；
- 条件组合：全部满足、任一满足、取反；
- 规则解释器：先计算结果草稿，校验通过后一次提交；
- 面向策划的规则试算：输入测试状态和行动，查看命中原因与变化前后。

### 借鉴但不照搬

- 借 GameAgentEngine 的权威世界状态、结构化动作、暂停/回调和世界步记录；
- 借 AgentWorld 的 Action/Perception 注册表与固定随机种子；
- 借 `json-rules-engine` 的 ALL/ANY 条件树；
- 借 `boardgame.io` 的纯行动函数、阶段和玩家视图测试方式；
- 不引入第二套 Agent Runtime，不允许规则脚本直接改数据库，不让模型决定正式数值。

### MVP 不做

- 自由代码脚本、复杂公式语言、通用物理模拟；
- 市场经济、派系、压力时钟等 Speeding 专属模块；这些先作为具体游戏规则实现。

### PM 验收

新增“财富、舆情、控制权、监管压力”四个状态项；配置“公开披露”行动；点击试算后，页面用中文说明哪些条件通过、四项数值如何变化；重复提交不重复扣减。

## 3. Agent / NPC

### 产品功能

从 Agent Hub 选择已有 Agent，赋予游戏身份、职责、权限、掌握的信息和初始关系。项目只保存映射；Agent 本体仍由 Agent Hub 管理。

### 可复用能力

- Agent、人格库、知识库和工具；
- H3 关系与多跳协作；
- H4 群组、频道和会话；
- H5 工作流、审批和投票；
- H6 情绪、认知、记忆和动态关系；
- H2 提示词合成、权限和完整留痕。

### 需要新增

- `GameCharacter`：项目内角色身份与 Hub Agent 引用；
- 角色可见信息、可执行行动、是否可推进流程；
- 导演角色与普通 NPC 的权限区分；
- 发布时冻结 Agent 配置版本、人格版本、知识版本和关系映射；
- 每局只把角色可见的世界信息投给对应 Agent。

### 借鉴但不照搬

- 借 GameAgentEngine 的 AgentRef、动作白名单和异步回调边界；
- 借 AgentWorld 的感知接口，但不引入其 Brain、Memory、AgentManager 和自动 tick；
- 不复制 Agent，不建设第二套人格、记忆、关系、消息或模型供应商。

### MVP 不做

- 自动生成完整人物、自动搭建组织；
- NPC 自主无限行动；
- 人格授予权限。人格只影响倾向，系统权限决定能否执行。

### PM 验收

将现有财务、法务、董事会对手 Agent 关联为三个 NPC；给法务设置“只能看法律与已披露事实”；试玩时查看三者收到的信息不同，所有咨询和回复可在协作记录中核对。

## 4. 事件与推进

### 产品功能

配置事件名称、触发条件、参与 NPC、展示内容、状态影响、是否推进时间、后续事件和结束条件。玩家仍可输入自然语言，事件不是固定选项菜单。

### 可复用能力

- H1 Run 承载一局游戏；
- H2 事件因果链、延迟结果、状态提交和重放；
- H3–H5 承载 NPC 协作、群组和决策；
- M0 的事件声明骨架。

### 需要新增

- 游戏局与回合状态机；
- 事件定义和局内事件实例分离；
- 触发条件、优先级、互斥、冷却、仅一次和每回合上限；
- 玩家自然语言 → 行动计划 → 玩家确认 → 正式行动；
- 导演负责呈现和推进，普通 NPC 只能建议或提交行动请求；
- 固定随机种子、暂停恢复、结局判定和完整复盘。

### 借鉴但不照搬

- 借 GameAgentEngine 的 ProposedAction、PendingResolution、TurnRecord；
- 借 AgentWorld 的 Scenario/Event 命名、快照和确定性随机数；
- 借 Ink 的 Continue/Choice/Tags/Checkpoint 接口，为未来大量文本内容保留适配口；
- 首版不用 Ink 作为权威规则，也不同时引入 Ink/Yarn；叙事变量不能修改财富等正式状态。

### MVP 不做

- 40 个事件、7–8 小时长局、复杂导演 AI；
- 玩家固定选项系统；
- 允许 Agent 自行宣称事件完成或擅自推进回合。

### PM 验收

配置一个“付款异常”事件：达到条件后出现，财务和法务被邀请处理；玩家用自然语言下达方案，系统先展示理解出的行动计划，确认后才结算；刷新或重启后可继续；复盘能解释事件为何出现、谁做了什么、数值为何变化。

## 5. 场景与视听

### 产品功能

建立场景，上传或选择背景图、人物立绘、音乐和音效；事件只引用场景与资源编号。替换资源不能改变游戏规则和结算。

### 可复用能力

- 现有文件上传、租户隔离和访问权限基础；
- H2 的正式事件可作为视听触发来源；
- M0 的版本与内容校验原则。

### 需要新增

- 统一资源库：图片、音频、版权来源、作者、尺寸/时长和版本；
- `Scene`：背景、出场角色、默认音乐和界面主题；
- 表现指令：切换场景、人物状态、字幕、音乐层、音效和转场；
- 资源预览、缺失资源提示、预加载、缓存和降级；
- PC/移动端、静音、字幕和减少动画支持。

### 借鉴但不照搬

- 借 Ink tags 的 speaker/portrait/sound 元数据思想；
- 借 Narrat/Dialogic 的场景、说话人、立绘和音频组织方式；
- 不引入完整 Godot/GDevelop 渲染和物理系统；
- 不把文件路径写进规则，规则只引用稳定资源编号。

### MVP 不做

- 3D、骨骼动画、视频编辑、复杂时间轴；
- AI 生成素材工作流和资产商城。

### PM 验收

建立“董事会会议室”场景，关联一张背景、三张人物图、一段音乐和一个提示音；试玩事件可正确切换。替换整套图片和音乐后，事件结果、数值和复盘完全一致；某个资源加载失败仍可继续游戏。

## 6. 试玩与发布

### 产品功能

策划可用当前草稿创建试玩局，查看玩家页面、NPC 协作、状态变化和问题清单。确认后点击发布，系统自动生成不可修改的游戏版本；正式游戏只从已发布版本开局。

### 可复用能力

- H1 的 Run 隔离、状态历史和版本锁定；
- H2 的事件、工具结果、成本和复盘；
- H7 的扩展权限、租户隔离和运营基础；
- M0 已有不可变内容哈希和安装注册表。

### 需要新增

- 试玩快照：锁定本次试玩所用草稿修订号；
- 发布检查：缺少规则、失效 Agent、断开的事件、缺失资源和权限冲突；
- `GameRelease`：冻结六类内容及依赖版本；
- 发布版本 → 内部游戏包的自动编译、校验、安装；
- 新局选用发布版本；旧局不被新版本改变；
- 玩家页与制作后台分离。

### 借鉴但不照搬

- 借 Ink 的预编译 bundle + 内容哈希 + checkpoint；
- 借 GDevelop 的 Preview/Debugger；
- 借 GameAgentEngine 的 timeline/state 检查；
- 不允许上传自由执行代码，不让“游戏包上传”成为普通策划的必经流程。

### MVP 不做

- 应用商店、公开发布平台、差分更新、灰度发布；
- 自动修复所有内容错误；首版只需清楚指出问题位置和修改入口。

### PM 验收

用 Speeding 小样完成一次：草稿试玩 → 查看问题 → 修正 → 发布 1.0.0 → 创建正式局。随后修改草稿并发布 1.1.0；1.0.0 的旧局保持原规则和资源，新局可选择 1.1.0；策划全程不接触游戏包文件和内部配置名。

## 四、实施优先级

六步是同一个产品流程，但不要求首轮把每一步做深：

| 批次 | 建设内容 | 阶段可验收产物 |
|---|---|---|
| G0 项目骨架 | 第 1 步 + 六步导航 + 草稿修订 | 能新建并重新进入 Speeding 小样 |
| G1 规则闭环 | 第 2 步 + 第 6 步的最小试玩 | 四个状态项和一个行动可试算、留痕 |
| G2 人物闭环 | 第 3 步 | 三个现有 Agent 成为可审计 NPC |
| G3 事件闭环 | 第 4 步 | 一个自然语言驱动的事件可从触发走到结算 |
| G4 表现闭环 | 第 5 步 | 一个事件有背景、人物、音乐和降级体验 |
| G5 发布闭环 | 完整第 6 步 | 一次点击生成不可变版本并创建正式局 |

M0 的“游戏机器实验室”保留为研发验收页，但不再承担策划制作入口。已有计数器和餐厅样例只用于回归底层协议，不出现在正式游戏项目列表中。

## 五、开源调研的最终使用边界

| 来源 | 采用 | 不采用 |
|---|---|---|
| AgentWorld | 场景声明、插件注册、动作/感知接口、固定随机、快照视图 | 第二套 Agent/记忆/事件总线、自动 tick、直接修改状态 |
| GameAgentEngine | 权威状态、结构化动作、异步等待、世界步审计 | 第二套 Runtime、关系、模型、任务 DAG 和管理后台 |
| Ink | 未来叙事适配接口、选择来源、标签、预编译内容和存档点 | 首版运行时、权威数值、游戏回合、直接执行外部副作用 |
| json-rules-engine | 条件树与命中解释 | 直接执行状态变化 |
| boardgame.io | 纯行动、阶段、玩家视图和确定性测试方法 | 整体替换当前后端和 Agent Hub |
| GDevelop / Narrat / Dialogic | 项目—场景—事件—预览的编辑体验与视听组织 | 完整引擎、物理系统和第二套权威状态 |

如复制任何开源实现的实质代码，必须按对应 MIT/ISC/Apache-2.0 许可证保留声明；当前主张是借鉴接口和产品模式、独立实现，不直接合并完整引擎。

## 六、不可违反的产品准则

1. 普通策划操作“游戏、状态、行动、人物、事件、场景、资源、试玩、发布”，不操作内部技术格式。
2. 页面不能要求用户理解 Schema、Manifest、Payload、Kernel 或内部 ID；必须保留时只能放入开发信息。
3. Agent、叙事和页面都只能提出行动，正式状态只能由规则服务校验后写入。
4. 游戏规则、人物映射和资源彼此通过稳定编号引用，不互相写死。
5. 已发布版本不可修改；升级产生新版本，旧局继续使用原版本。
6. Speeding 专有名词和规则只存在于 Speeding 游戏项目及其发布版本，不进入 Agent Hub 或通用游戏内核。
7. 每个批次必须提供 PM 可点击、可观察、可复述的验收页面；只有接口和数据库表不算完成。
