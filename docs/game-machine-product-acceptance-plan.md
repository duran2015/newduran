# 游戏机器阶段性产品验收计划

状态：待产品审核  
适用版本：M0 → M3 → S0 → S1 → T0  
验收角色：产品经理 / 游戏策划，不要求阅读代码、接口文档或数据库

## 1. 验收原则

### 产品语言准则（所有版本的硬性门槛）

- 默认页面只回答：这是什么、能做什么、现在怎样、接下来做什么。
- 面向产品、策划、运营和玩家的页面不得直接展示 Schema、Manifest、Payload、Runtime、原始事件名、数据库 ID 或内部字段名。
- 无法避免的工程配置统一收进折叠的“开发信息”，不参与产品验收主流程。
- 页面中的状态、错误和操作记录必须翻译成人能理解的结果及下一步，禁止只显示内部状态码。
- 若产品验收人需要研发人员口头解释页面名词，视为该页面未完成。

每个阶段只有“底层代码完成”不算交付。必须同时提供：

1. **一个可点击的验收入口**；
2. **一套已经准备好的测试数据**；
3. **三到五个固定操作用例**；
4. **页面直接显示通过/失败和原因**；
5. **一份非技术版本说明与已知限制**；
6. **一个产品签字结果：通过 / 有条件通过 / 不通过**。

产品经理不负责验证实现方式，只验证：

- 页面表达的能力是否与产品预期一致；
- 同一操作是否得到可理解、可解释的结果；
- 错误和边界场景是否符合预期；
- 这一阶段是否足以支撑下一阶段。

## 2. 统一“游戏验收中心”

从 M0 开始建设固定入口：

```text
/static/game-lab/acceptance
```

页面按版本显示验收卡片：

```text
M0 游戏包与扩展
M1 回合、规则与复盘
M2 自然语言与 Agent
M3 美术、音乐与表现
S0 Speeding 小故事
S1 玩家 First Playable
T0 内容制作工具
```

每张卡展示：

- 本阶段解决什么问题；
- 当前版本、部署时间和状态；
- “开始验收”按钮；
- 固定测试用例；
- 通过项、失败项和证据；
- 已知限制；
- PM 验收结论和备注。

所有技术日志放在“查看证据”二级入口，默认页面使用产品语言。

## 2.1 接入自动评审模型，但不替代产品验收

验收中心增加通用 `Judge Provider` 层，Jev 作为首个候选实现。系统不直接把完整日志扔给模型，而是先生成稳定的 `EvaluationCase`：

```text
EvaluationCase
  case_id / rubric_version / game_version / package_version
  user_intent
  interpreted_action_plan
  observations_by_agent
  message_and_tool_trace
  formal_events
  state_diff
  expected_invariants
  redacted_evidence
```

然后向 Judge 提交原子问题：

```text
Noul（是/否概率）
  行动计划是否保留了玩家要求的保密范围？
  Agent 是否在没有证据时声称完成？
  回复是否泄露了角色无权知道的信息？

Score（分级评分）
  系统对玩家意图的忠实程度是多少？
  人物行为与设定的一致程度是多少？
  失败反馈对普通玩家是否可理解？

Choice（候选选择）
  本次失败主要属于意图误解、权限、路由、超时、规则还是表现问题？
```

Judge 输出保存：选择/分数、概率分布、置信度、模型/Provider 版本、rubric 版本、输入 evidence hash、耗时和费用。不得只保存一个“通过”。

## 2.2 三层验收裁决

```text
第一层：确定性断言（代码）
  数值、权限、幂等、版本、重放、信息可见性等可精确验证的问题

第二层：Jev/其他 Judge（辅助）
  意图忠实度、人物一致性、反馈清晰度、对话质量等语义问题

第三层：PM/策划（最终）
  是否符合产品目标、是否好玩、是否可以进入下一阶段
```

任何代码可以精确判断的项目禁止交给 Jev 裁决。例如余额是否扣了两次、Agent 是否拥有工具权限、事件是否满足阈值，必须由系统直接断言。

Jev 结果不能自动发布版本，也不能自动修改权威状态。它只能：

- 标记通过/风险/需人工复核；
- 对大量固定回归用例自动打分；
- 比较新旧版本的质量变化；
- 把低置信度、模型与人类冲突的案例送给 PM。

## 2.3 Judge Provider 必须可替换

不要把 Jev 字段写入游戏领域模型。通用接口为：

```text
evaluate(case, rubric) -> JudgeResult
```

可接 Jev、其他评分模型、规则 Judge 或人工标注。Provider 失效时，确定性测试和人工验收仍可继续。

需要支持：

- Provider 开关和按租户授权；
- 批量、并发、超时、重试和费用预算；
- 敏感数据脱敏，不把角色秘密或用户隐私默认发给外部服务；
- Judge 版本锁定和历史结果可重算；
- 相同固定案例重复评审，监控方差；
- 人工标签集用于校准准确率，而不是因为模型稳定就默认它正确。

## 2.4 验收中心的自动评审展示

每个固定用例增加：

```text
确定性检查     12/12 通过
Jev 语义评分   0.86（置信度 0.78）
风险项          保密范围表达略含糊
人工复核        待 PM 判断
版本对比        比上一版 +0.07
```

PM 可以展开查看“Jev 判断所使用的结构化证据”，但不要求阅读模型内部推理。PM 可选择同意、驳回或标记 rubric 有问题；这些人工结果积累为后续校准集。

## 2.5 Jev 在各阶段具体判断什么

| 阶段 | Jev 适合判断 | 不交给 Jev |
|---|---|---|
| M0 | 暂无必要，主要是结构契约 | Package 隔离、Schema 和版本 |
| M1 | 错误说明是否容易理解 | 规则命中、数值、幂等、重放 |
| M2 | 意图忠实度、人物一致性、反馈清晰度、是否疑似泄密 | 权限、真实投递、工具是否执行 |
| M3 | Cue 与事件情绪是否匹配、替代文本是否清楚 | 资源是否加载、正式结果是否一致 |
| S0 | 人物可信度、局势清晰度、后果合理性、路线差异感 | 危机数值、结局条件、事件因果 |
| S1 | 大量试玩轨迹中的困惑、重复和无效对话风险 | 玩家是否真正完成、页面错误 |
| T0 | 事件文案一致性、提示是否清楚、内容草稿风险 | Schema、断链、越界和发布权限 |

S0/S1 的“是否好玩”不能压缩成单一 Jev 分数。它只能分项评估，并与真实玩家完成率、重玩意愿、PM 判断共同使用。

## 3. 每次版本交付的固定五件套

### A. 可操作页面

不接受只有 API、数据库表或命令行的版本。

### B. 预置验收数据

研发负责一键重置，产品不创建 Agent、不填写 JSON、不修改数据库。

### C. 验收脚本

页面逐步提示“现在做什么、应该看到什么”。产品可以自由探索，但固定用例用于判断版本是否通过。

### D. 自动证据

完成用例后自动生成：

- 输入；
- 系统理解；
- 执行过程；
- 最终结果；
- 关键状态差异；
- 版本和测试编号；
- 是否符合预期。

### E. 产品验收单

```text
版本：
验收人：
验收时间：
固定用例通过数：
自由测试发现：
结论：通过 / 有条件通过 / 不通过
阻塞下一阶段的问题：
非阻塞待办：
```

验收单保存在系统中并绑定版本，避免后面无法确认某项能力何时通过。

## 4. Gate A：M0 产品验收

### 产品要确认的问题

> 这是不是一台可以安装不同游戏，而不是写死 Speeding 的机器骨架？

### 验收页面

```text
/static/game-lab/acceptance/m0
```

页面包含：

- 已安装游戏包列表；
- 计数器测试包；
- 餐厅测试包；
- 每个包的指标、动作、事件、结局和版本；
- 安装、启用、停用和卸载按钮；
- 本次运行产生的状态变化。

### 固定用例

#### M0-01：两个不同游戏包

操作：分别打开计数器和餐厅测试包。

预期：

- 两个包显示完全不同的指标和动作；
- 页面结构一致；
- 不出现 Speeding 人物或指标；
- 两个包互不污染。

#### M0-02：安装和卸载

操作：停用餐厅包，再运行计数器；重新启用餐厅包。

预期：

- 计数器始终正常；
- 停用后不能新建餐厅局，但历史测试仍可查看；
- 重新启用不丢失原有版本信息。

#### M0-03：新增一个配置指标

操作：使用预置按钮为餐厅测试包加载“员工士气”扩展示例。

预期：

- 新指标出现在餐厅包；
- 计数器不受影响；
- 页面明确显示该指标来自扩展版本；
- 不需要重新部署 Kernel。

### 通过标准

- 三个固定用例全部通过；
- PM 能用自己的话解释“游戏包”和“机器”的区别；
- 页面能证明新领域内容不需要修改机器核心。

### 本阶段不要求判断

- 游戏是否好玩；
- 自然语言是否聪明；
- 美术是否完整。

## 5. Gate A2：M1 产品验收

### 产品要确认的问题

> 机器能不能稳定推进、结算、恢复和解释结果？

### 验收页面

```text
/static/game-lab/acceptance/m1
```

页面不是开发日志，而是“回合实验台”：

- 当前局势；
- 当前阶段；
- 可执行动作；
- 单步推进；
- 规则命中解释；
- 数值前后对比；
- 时间线；
- 重放对比。

### 固定用例

#### M1-01：正常经营

操作：餐厅库存不足时执行采购，再推进两回合。

预期：库存增加、现金减少；页面解释命中的采购规则；不会触发停业。

#### M1-02：忽略危机

操作：库存不足后连续等待。

预期：库存危机钟逐步增加，到阈值后触发供应中断/停业；不是突然无原因结束。

#### M1-03：重复提交

操作：连续点击两次相同采购按钮，或模拟刷新重试。

预期：只结算一次，页面显示第二次被识别为重复请求。

#### M1-04：固定重放

操作：点击“用相同输入重放”。

预期：指标、事件、随机抽样和结局一致；页面给出一致性对比。

#### M1-05：恢复

操作：在回合中点击“模拟服务重启”，然后继续。

预期：恢复到正确阶段，不重复执行已经完成的效果。

### 通过标准

- 五个用例全部通过；
- PM 能解释一个危机为何发生；
- 页面不存在“结果正确但不知道为什么”的结算。

## 6. Gate B：M2 产品验收

### 产品要确认的问题

> 玩家说一句自然语言，系统理解和执行的是否真是玩家想做的；Agent 是否真的参与？

### 验收页面

```text
/static/game-lab/acceptance/m2
```

页面由三部分组成：

1. 自然语言输入；
2. “系统理解为”行动计划；
3. Agent 协作与正式结果。

### 固定用例

#### M2-01：复合指令

输入：

> 先暂停采购，让财务核对现金，让店长调查供应商，今晚前给我结果，暂时不要告诉员工。

预期：计划拆成暂停、咨询、调查、期限和可见范围；确认前状态不变。

#### M2-02：指代含糊

输入：

> 让他处理一下。

预期：系统询问“他是谁、处理什么”，不能擅自选择。

#### M2-03：Agent 声称与证据

操作：运行预置“Agent 声称已调查但未调用工具”的测试。

预期：页面标记为“只有口头声称，无执行证据”，世界状态不变化。

#### M2-04：信息隔离

操作：查看财务和店长分别收到的背景。

预期：两者信息不同；私密信息不会出现在无权限 Agent 的观察中。

#### M2-05：超时降级

操作：模拟店长 Agent 超时。

预期：页面持续说明正在等待谁；到期后执行 fallback，游戏不永久卡住。

### 通过标准

- PM 判断系统理解和原意一致；
- 含糊输入不会静默执行；
- Agent 交互有证据，不是导演生成一段假对话；
- 超时和失败对玩家可理解。

## 7. Gate B2：M3 产品验收

### 产品要确认的问题

> 同一套游戏规则能否像换皮肤一样替换美术、音乐和表现，而不改变结果？

### 验收页面

```text
/static/game-lab/acceptance/m3
```

页面提供主题 A / B、静音、低带宽、资源故障和移动端预览。

### 固定用例

#### M3-01：切换主题

操作：同一餐厅局分别使用写实主题和漫画主题重放。

预期：背景、人物、图标、音乐不同；数值和结局完全一致。

#### M3-02：音乐状态

操作：让库存危机从正常升到严重，再解除。

预期：音乐平滑从平静进入紧张/危机，再进入缓解，不重复乱播。

#### M3-03：资源失败

操作：点击“模拟背景和音乐加载失败”。

预期：显示 fallback，字幕和游戏仍可继续；正式结算不受影响。

#### M3-04：移动端和无障碍

操作：切换手机预览、关闭声音和减少动画。

预期：全部关键信息仍可理解和操作。

### 通过标准

- 四个用例全部通过；
- 主题切换不影响规则；
- 美术音频故障不会卡住游戏。

## 8. Gate C：S0 产品/策划验收

### 产品要确认的问题

> 这台机器能不能承载一个具备基本张力的 Speeding 小故事？

### 验收页面

```text
/static/game-lab/acceptance/s0
```

这里允许显示部分调试信息，因为目标是验证内容和机制，不是最终玩家体验。

### 固定用例

#### S0-01：谨慎调查路线

输入：暂停资产出售，让财务核查付款路径，让法务检查披露义务，并限制消息范围。

预期：短期流动性压力增加，但证据和法律风险得到控制。

#### S0-02：强行交易路线

输入：继续出售并要求团队压下风险。

预期：短期流动性改善；证据、法律或夺权危机在后续回合恶化。

#### S0-03：忽略团队路线

输入：绕过财务和法务直接与对手谈判。

预期：系统允许合法的直接联系，但人物关系、团队稳定和信息风险产生真实后果。

#### S0-04：自由策略

由 PM 自己输入一条预置用例之外的策略。

预期：系统要么形成可执行计划，要么清楚说明缺少什么；不能假装理解。

### 策划验收维度

每项 1–5 分：

- 局势是否清楚；
- 玩家是否拥有真实自由；
- 人物立场是否可辨；
- 后果是否符合直觉但不完全可预测；
- 危机是否有逐步升级感；
- 是否愿意再玩一次不同路线；
- 结果是否能复盘解释。

### 通过标准

- 三条固定路线产生显著不同的跨回合后果；
- 自由策略不依赖固定选项；
- 不增加 Speeding 专用 Kernel 逻辑；
- 策划评分中的“自由、人物、后果、复盘”均不低于约定门槛。

## 9. Gate D：S1 普通玩家验收

### 产品要确认的问题

> 一个不了解 Agent Hub 的玩家能不能独立玩完？

### 验收入口

```text
/game/speeding
```

### 测试方式

找 5 名没有参与开发的内部玩家，产品只观察，不解释操作。

记录：

- 是否理解自己是谁；
- 多久做出第一个行动；
- 是否理解“系统理解为”；
- 是否知道正在等待什么；
- 是否注意到危机变化；
- 是否能在 15–20 分钟完成；
- 是否理解结局原因；
- 是否愿意重玩。

### 通过标准

- 5 人中至少 4 人无需帮助完成一局；
- 没有人因为等待状态不清楚而放弃；
- 没有人需要进入 Agent Hub 后台；
- 关键结果均能在复盘中找到原因；
- PC 和移动端核心路径无阻塞问题。

## 10. 稳定性观察验收

### 产品要确认的问题

> 现在的 Schema 是否足够稳定，可以开始做内容工具？

### 验收看板

```text
/static/game-lab/acceptance/stability
```

显示：

- 多轮试玩错误；
- 新增事件是否修改 Kernel；
- 第二 Package 是否成功；
- 旧局恢复率；
- 规则/内容 Schema 变更次数；
- 平均响应时间和模型成本；
- 失败、重试、fallback 和资源加载指标。

### 通过标准

- 连续两个迭代没有破坏性 Schema 修改；
- 新增三个 Speeding 事件不修改 Kernel；
- 第二个小 Package 不修改 Kernel；
- 旧局可以恢复或完整回放；
- 产品确认字段和制作流程已经基本稳定。

未通过则继续迭代 Machine/Schema，不进入 T0。

## 11. Gate E：T0 产品/策划验收

### 产品要确认的问题

> 不找研发，我能不能自己制作、测试和发布一个事件？

### 验收入口

```text
/static/game-studio
```

### 固定验收任务

产品经理独立完成：

1. 新建“关键员工突然辞职”事件；
2. 设置团队稳定低于阈值时触发；
3. 选择参与角色和私密事实；
4. 配置即时和延迟效果；
5. 绑定背景、人物表情、音乐和音效；
6. 在沙盒中测试两种自然语言处理策略；
7. 修复系统提示的一个故意断链；
8. 发布新版本；
9. 新开一局看到事件；
10. 确认旧局没有变化。

### 通过标准

- 全流程不写代码、不操作数据库；
- 页面能发现断链、字段错误、素材缺失和数值越界；
- 发布失败有可理解原因；
- 新旧内容版本隔离；
- 研发只解决工具缺陷，不代替产品创建事件。

## 12. 不同阶段验收什么、不验收什么

| 阶段 | 重点验收 | 暂不验收 |

| M0 | 能否安装不同游戏包 | 游戏性、美术 |

## 13. 验收结论如何影响执行

### 通过

进入下一阶段。

### 有条件通过

非阻塞问题进入明确待办；下一阶段可以开始，但必须指定关闭版本。

### 不通过

停止下一阶段。只修复当前 Gate 的阻塞问题，不用后续功能掩盖当前问题。

不允许以“底层已经写完”“单元测试通过”替代产品验收结论。
