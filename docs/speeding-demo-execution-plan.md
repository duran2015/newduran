# Speeding 基础 Demo 执行计划

状态：待产品审核  
版本目标：通用 Game Kernel v0 + Speeding First Playable  
主线关系：Agent Hub H1–H7 保持平台化；本计划属于 Speeding G0–G2 垂直应用

> **总原则：先造一台简单的游戏机器（架构设计时考虑未来扩展性），再用一个很小的 Speeding 故事证明它能工作；机器跑稳后，才把安装内容的过程做成傻瓜式工具。**

## 0. 实施顺序纠正

本计划不是“先做五个事件，再从事件中抽象系统”，也不是“首个 Demo 就完成傻瓜式内容生产平台”。正确顺序是：

```text
第一步：先完成通用 Game Kernel
  回合 / Command / Event / Rule / Effect / Clock / Ending /
  Version / Replay / Presentation Cue

第二步：用两个极小技术样例验证通用性
  非 Speeding 规则夹具 + Speeding 单事件夹具

第三步：把五事件 Speeding 小故事作为内容包装进去
  不新增底层特殊逻辑，只配置内容并绑定 Agent/素材

第四步：做独立玩家页面，形成 First Playable

第五步：Schema 经真实试玩稳定后，再建设傻瓜式 Content Studio
```

因此，五事件 Demo 是底层机制的**验收内容包**，不是底层机制本身；“填空 → 检查 → 发布”的可视化制作平台是后续产品化阶段，不应反过来决定尚未稳定的底层协议。

## 1. 本次只证明什么

用一局 20–30 分钟的可玩 Demo 证明：

1. 玩家不依赖固定选项，可以用自然语言处理局势；
2. 系统能把自然语言转换成可确认的行动计划，而不是让模型直接改世界；
3. 多个 Agent 拥有不同身份、信息和立场，会真实咨询、汇报、反对或隐瞒；
4. 财富、权力、法律和舆情由 Game Core 统一结算并产生跨回合后果；
5. 每一项数值变化、Agent 通信和最终结局都可以复盘；
6. 玩家只进入独立游戏页，不需要理解 Agent Hub 管理后台；
7. 五事件内容包能在不修改 Game Kernel 的情况下被装载、运行、卸载和替换。

Demo 不用于证明七八小时内容量、完整 UGC 平台、完整傻瓜式编辑器、实时生图或大规模 NPC 社会。

## 1.1 不可妥协的核心原则：Demo 小，协议不能是 Demo 级

本次可以只有五个事件、五个角色和一张游戏页，但不得把它们写死在代码中。所有实现必须能够在不重写已有存档、不修改 Agent Hub Core、不停止全部在线游戏的前提下扩展到更多世界、事件、角色、玩法和租户。

任何为了“先跑起来”而绕过以下约束的实现，不算完成：

1. 不把 Speeding 角色名、事件名、指标名硬编码进 Hub 或通用 Game Core；
2. 不以数据库当前结构或 Prompt 文本充当正式游戏协议；
3. 不允许发布内容后原地修改，运行中的局必须绑定不可变版本；
4. 不允许 Agent、脚本或前端直接写世界状态；
5. 不允许新增玩法时必须修改一个不断膨胀的核心 `switch`；
6. 不允许升级后无法重放旧局、解释旧结局或恢复等待中的任务；
7. 不允许通过任意脚本换取扩展性，所有扩展必须声明权限、读写范围和版本。

## 2. Demo 主题与体验边界

### 2.1 开局

玩家是刚刚跨过万亿美元门槛的科技首富。集团同时出现资产流动性压力、监管调查和董事会权力斗争。一笔高风险资产出售可以暂时缓解现金压力，但其中牵涉秘密款项、政治交易和人物私事。

### 2.2 角色

首版只使用 5 个角色，全部复用 Agent Hub：

| 角色 | 游戏职责 | 默认立场 |
|---|---|---|
| 导演 Agent | 选择已发布事件、组织反馈，不改数值 | 保持节奏和冲突 |
| 财务负责人 | 现金、资产、交易方案 | 优先保住流动性 |
| 法务负责人 | 合规、监管、证据和披露 | 优先降低法律风险 |
| 舆情/政治顾问 | 媒体、公众、政治人物 | 优先维护影响力 |
| 董事会对手 | 控制权、联盟、问责 | 借危机削弱玩家 |

### 2.3 权威世界指标

首版固定 8 个，不开放任意字段：

```text
现金流动性
净资产
公司控制权
公众声誉
法律风险
政治影响力
团队稳定度
证据暴露度
```

### 2.4 危机钟

```text
流动性断裂：到期后触发债务违约/强制出售
监管调查：到期后触发传唤/冻结/起诉候选
董事会夺权：到期后触发临时董事会和控制权表决
```

每个危机钟拥有当前值、升级阈值、期限、缓解规则和爆发事件。

### 2.5 五个主事件

1. 高风险资产出售与付款路径异常；
2. 私人关系/网红事件被媒体掌握；
3. 政治候选人要求公开支持和资金协助；
4. 监管机构要求披露关联交易；
5. 董事会利用前三项危机发起夺权。

事件不提供固定三选一。每个事件只定义事实、约束、参与者、可用行动词汇和确定性后果规则。

### 2.6 首版结局

- **暂时稳住**：保住控制权并解决短期流动性，但留下未来债务；
- **被董事会架空**：资产仍在，但公司控制权跌破阈值；
- **监管冻结**：法律风险和证据暴露共同越线；
- **主动退场**：玩家主动放弃部分财富或权力，换取声誉/安全。

## 3.4 长期扩展架构红线

### A. 四层必须独立

```text
Agent Hub
  通用 Agent、关系、协作、记忆、权限、审计

Game Core
  通用会话、回合、动作、规则、效果、随机、存档、复盘

Game Package
  Speeding 世界 Schema、角色、事件、指标、行动和结局

Presentation Runtime / Asset Library
  场景、角色表演、美术、音乐、音效、配音、字幕和动效编排

Player App / Content Studio
  玩家呈现与策划制作，不拥有权威状态
```

未来新增“崇祯”“公司经营”“宫廷政治”等游戏，应新增 Game Package 和玩家主题，而不是复制一套 Runtime。

### B. 所有核心对象版本化

正式记录至少固定以下版本：

```text
game_core_version
world_schema_version
content_bundle_hash
ruleset_version
effect_catalog_version
intent_schema_version
prompt_bundle_version
model_policy_version
ui_projection_version
```

存档恢复和复盘必须使用创建时的版本；新版本不能静默改变旧局结果。

### C. 稳定 ID 与引用，不按名称关联

- 角色、指标、事件、结局、工具、关系类型和资源都使用不可变稳定 ID；
- 名称、文案、图片、排序和标签可修改；
- 删除改为 deprecated，不物理破坏历史引用；
- 改名不修改 ID；
- 内容发布时执行引用完整性检查。

### D. Registry + Contract，不写死玩法

以下能力通过注册表扩展：

- `ActionTypeRegistry`：动作及参数 Schema、权限和 resolver；
- `EffectTypeRegistry`：效果及允许写入路径、校验和回放方式；
- `FactCatalog`：规则可以读取的事实；
- `ConditionOperatorRegistry`：允许使用的条件算子；
- `EventTypeRegistry`：事件类型和玩家投影；
- `ProjectionRegistry`：同一正式状态面向不同角色和 UI 的视图；
- `EndingEvaluatorRegistry`：结局策略，但最终输出仍是标准候选。

新增扩展必须提供 manifest、版本、JSON Schema、权限、幂等语义、确定性声明、迁移策略和测试 fixture。禁止运行任意未审核脚本。

### E. Command / Event / Projection 分离

```text
Command / ActionProposal：想做什么
Domain Event：系统确认发生了什么
Projection：玩家、角色和后台分别看到什么
```

界面和 Agent 都只提交 Command；Game Core 产生 Domain Event；读页面通过 Projection 构建。不得让某个页面字段反向成为权威状态。

### F. 事件日志为历史依据，快照只负责加速

- 正式 Action、Effect、RandomDraw、StateChange 均保留因果链；
- 定期生成版本化快照，加速恢复；
- 快照损坏时可以从日志重建；
- 旧事件必须可通过 upcaster 读取；
- 迁移不能改写已经发生的事件含义。

### G. 数据迁移必须向前兼容

- 每次 Schema 变化都提供 migrate、rollback 或明确的不可回滚说明；
- 支持旧存档只读回放；
- 长时间等待的 callback/工作流升级后仍能恢复；
- 数据库迁移与应用发布采用 expand → migrate → contract，不在一次发布中先删旧字段；
- 发布前用生产数据结构的匿名副本验证迁移。

### H. Schema 驱动 UI

- 内容表单、行动计划参数、指标显示和调试信息尽量由 Schema/metadata 生成；
- 新增指标或动作时，不要求同时修改多个硬编码页面；
- 自定义 UI 作为可选 renderer 注册，缺少 renderer 时仍有通用表单和通用展示；
- PC、移动端使用同一数据投影，不维护两套业务逻辑。

### I. 异步优先和容量边界

- 模型调用、Agent 协作、生图和批量结算均为异步任务；
- 请求拥有 idempotency key、deadline、重试、取消和 dead-letter；
- 每局、每回合、每 Agent 和每条因果链有并发与 Token 预算；
- 用 Activation/LOD 控制 Agent 数量，不能随角色增长线性全量调用；
- 玩家页面通过事件流或轮询查询进度，不保持长同步等待链。

### J. 多租户、安全与资源隔离

- 所有游戏、内容、事件、存档和素材都带 tenant/game/package 边界；
- 能力包只能读写 manifest 声明的状态路径和工具；
- 私密信息、角色 Observation 和后台审计使用不同投影；
- 限流、费用、模型和存储按租户/游戏计量；
- 一个扩展失败不能拖垮其他游戏或 Hub 主进程。

### K. 可观测性是发布条件

每个回合必须能回答：

- 卡在哪个阶段；
- 正在等待哪个 Agent/工具；
- 为什么某条规则命中或未命中；
- 哪个版本产生了结果；
- 消耗多少时间、Token 和工具调用；
- 是否发生重试、降级、重复提交或死信。

日志、指标、Trace、审计和玩家复盘共享 trace/root/parent ID，但展示权限不同。

### L. 灰度、回滚和功能开关

- 新规则、新模型、新 Prompt 和新内容先进入 Draft/Canary；
- 已开始的局默认不切换版本；
- 新局可以按百分比、租户或测试账号灰度；
- 发现问题时停止新局使用新版本，不破坏旧局；
- 部署与内容发布是两个独立动作，可以分别回滚。

### M. 表现层与规则层分离

Game Core 只产生正式事实和 `PresentationCue`，不关心使用图片、动画、文字、音乐还是语音。Presentation Runtime 根据主题包、设备能力、语言、可访问性和用户设置，把同一个 Cue 渲染成具体体验。

```text
Domain Event / State Diff
  -> Presentation Projector
  -> PresentationPlan
       scene / background / character pose / expression
       dialogue / caption / key art / transition
       music state / ambience / sfx / voice
  -> Web / Mobile Renderer
```

表现失败只能降低体验，不能阻塞或改变权威结算。图片加载失败时仍显示文本；音频失败时仍可继续回合；实时生成失败时回退到已审核素材。

### N. 资源全部通过 Asset Manifest 管理

禁止在事件代码和页面组件中写死文件路径。每个资源使用稳定 `asset_id`，通过版本化 Manifest 解析：

```text
asset_id
asset_type                 portrait/background/key_art/icon/music/sfx/voice/video
version / content_hash
uri variants               desktop/mobile/low_bandwidth
locale variants
character / scene / mood / tags
duration / loop points / loudness
license / author / provenance / allowed_usage
moderation_status
fallback_asset_id
preload_policy / cache_policy
```

游戏内容只引用语义资产，如 `character.cfo.expression.anxious`、`scene.boardroom.night`、`music.crisis.level_2`。更换画风、语言或移动端资源时不修改事件定义。

### O. Presentation Cue 是稳定协议

首版支持以下通用 Cue：

```text
EnterScene / ExitScene
SetBackground
ShowCharacter / HideCharacter
SetExpression / SetPose
FocusSpeaker
ShowDialogue / ShowNarration / ShowHeadline
ShowMetricChange / ShowEvidence / ShowEndingCard
PlayMusic / SetMusicIntensity / StopMusic
PlayAmbience / PlaySFX / PlayVoice
Transition / CameraEffect / UIEmphasis
```

Cue 保存 `source_event_id`、顺序、开始条件、可跳过性、阻塞性、持续时间和 fallback。LLM 可以建议表现标签，最终只能从已发布 Cue/Asset Catalog 中选择，不能输出任意文件地址或脚本。

### P. 音频状态机与混音规则

音乐不能按每条消息简单播放文件。Presentation Runtime 维护独立音频状态：

- 音乐按 `calm / tension / crisis / resolution / ending` 切换；
- 危机钟可驱动音乐层级和强度，但不改变危机值；
- 支持淡入淡出、循环点、交叉过渡和不中断续播；
- 对话/配音出现时自动压低音乐和环境音；
- SFX 分 UI、事件、环境和强调四类并有限流，避免连续轰炸；
- 所有音频保存响度、循环、语言和版权元数据；
- 用户可分别调节音乐、音效、配音，支持一键静音。

### Q. 角色视觉不是一张头像

角色资源按稳定身份维护：

```text
角色基础造型
服装/时期
姿态
表情
伤病/压力等状态变体
头像/半身/全身尺寸
移动端裁切安全区
```

Agent 的情绪值不能直接拼文件名；Presentation Projector 先把正式人物状态映射成受控的表现标签，例如 `guarded`、`angry`、`exhausted`，再由主题包解析到具体素材。

### R. 生成式素材只是异步生产管线

实时生图、TTS 或视频不能成为正式世界推进的同步依赖：

```text
生成请求
-> 安全/版权/人物一致性约束
-> 异步生成
-> 审核或自动质量门禁
-> 内容寻址存储
-> Asset Manifest 注册
-> 缓存后展示
```

固定角色和关键剧情优先使用人工确认的 Canonical Asset。实时生成只用于非关键场景、玩家主动请求或个性化回顾；相同关键事件在同一内容版本中默认使用稳定素材，避免画风和人物漂移。

### S. 美术方向也是版本化内容

每个 Game Package 绑定 `ArtDirectionVersion` 和 `AudioDirectionVersion`：

- 色彩、构图、字体、图标、人物比例和禁用风格；
- 角色视觉锚点、服装与道具连续性；
- 音乐主题、乐器、速度、情绪和禁用声音；
- Prompt 模板、参考图和负面约束；
- UI token、动效速度和场景转场规范。

这样未来可以为同一规则包提供写实、漫画或极简等不同主题，而不复制游戏逻辑。

### T. 媒体发布和线上稳定性

- 大资源存对象存储/CDN，不进入数据库和应用镜像；
- 图片提供多尺寸和现代格式，音频按流式/预加载策略分级；
- 场景开始前预取本回合高概率资源，低概率资源按需加载；
- Manifest 发布为不可变版本并支持 CDN 回滚；
- 记录加载失败率、首屏资源时间、音频启动失败和缓存命中率；
- 提供低带宽、关闭动画、关闭实时生图和纯文字模式；
- 所有对话有字幕，关键信息不能只靠颜色或声音表达。

## 4. 核心运行链路

```text
Game Core 生成本回合 GameView
  -> 玩家自然语言输入
  -> Intent Interpreter 输出 ActionPlan
  -> Game Core 校验目标、权限、资源、期限和歧义
  -> 玩家确认/修改计划
  -> Hub 执行咨询、委派、会议或审批
  -> 回调聚合 Agent 的 Advice / Vote / Proposal
  -> Resolver 冻结输入并结算 typed effects
  -> ToolResultService 原子写入状态和正式事件
  -> 评估危机、后续事件与结局
  -> Narrator 只根据正式结果生成反馈
  -> 进入下一回合
```

普通角色没有 `advance_turn` 和状态写权限。导演只能请求呈现或候选事件，不能写指标。

## 5. 首版行动与效果词汇

### 5.1 玩家可表达的行动

自然语言不受按钮限制，但首版编译到以下受控动作：

```text
investigate        调查事实
consult            咨询角色
delegate           委派任务
convene            召集会议
allocate_funds     拨款
pause_transaction  暂停交易
approve_transaction 批准交易
disclose           主动披露
issue_statement    公开声明
negotiate          谈判/交换条件
appoint_remove     任命或撤换
wait               等待并推进时间
```

首版无法编译的行动会得到原因和可执行改写建议，不会偷偷替换玩家意图。

### 5.2 Game Core 可提交的效果

```text
AdjustMetric
SetFlag
AddPressure
RelievePressure
CreateCommitment
Fulfill/BreachCommitment
ChangeRelation
RevealFact
CreateClaim
SpawnEvent
ScheduleEffect
EndGame
```

每个效果必须声明来源规则、before/after、可见范围、幂等键和因果事件。

## 6. 阶段拆分

## 阶段 D0：规格冻结与页面原型

目标：所有人先看到同一个 Demo，不在开发过程中继续扩大范围。

任务：

- 冻结 8 个指标、3 个危机钟、12 个行动和 12 类效果；
- 冻结五个事件的事实、触发、可见性和主要后果；
- 定义 GameSession、Turn、ActionPlan、Event、Effect Schema；
- 制作玩家游戏页、计划确认层、结局页和复盘页的静态原型；
- 冻结首版 Art Direction、Audio Direction、角色视觉锚点和场景 Cue 示例；
- 定义 Hub 与 Game Core 接口，不修改 Hub 通用领域模型。

页面验收：

- 产品经理能从开局页进入第一回合；
- 能输入自然语言并看到计划确认层；
- 能看到人物、指标、危机钟和时间线的位置；
- 原型中不出现 Agent Hub 工程术语。

退出物：Schema v1、接口约定、五事件内容表、四页原型、视听方向板和一份完整场景 Cue Sheet。

## 阶段 D1：G0 确定性 Game Core

目标：完全关闭模型后，脚本玩家也能跑完整局。

任务：

- GameSession/Turn 持久化；
- 7 阶段状态机及非法跳转保护；
- 事件条件、优先级、权重、互斥、冷却和 once；
- 固定种子随机与 RandomDraw 审计；
- typed effects 与状态不变量；
- 危机钟、承诺和结局优先级；
- before/after diff 和规则解释树；
- policy bot 与固定种子回归测试。

页面验收：

- “测试运行”页面可自动跑完一局；
- 每回合能看到触发事件、执行效果和状态差异；
- 相同 seed 和输入得到相同结果；
- 非法数值修改被明确拦截。

退出标准：连续 100 局无卡死；四个结局均可达；所有变化有来源。

## 阶段 D2：G1 自然语言行动

目标：玩家可以不用固定选项完成一局。

任务：

- Intent Interpreter 的结构化输出 Schema；
- 对象、期限、保密范围、预算、委派和审批步骤提取；
- 信心分数和歧义列表；
- 计划预览、编辑、确认、取消；
- 越权、资源不足、互斥与未知行动反馈；
- 建议行动生成，但保持非强制；
- 50 条自然语言回归样本。

页面验收：

- 输入一句复合指令能拆成多步计划；
- 模糊对象会询问，不擅自选择；
- 玩家能删除、调序和修改步骤；
- 确认前世界状态不会改变。

退出标准：核心 12 类行动识别通过率达到验收样本要求；任何无法解释的计划不得执行。

## 阶段 D3：Agent Hub 社会接入

目标：让角色真正参与，而不是由导演一人伪装所有人物。

任务：

- 创建并绑定五个 Demo Agent；
- 为每个角色生成裁剪后的 Observation；
- 区分 Fact、Claim、Belief 和 Secret；
- 接入咨询、委派、会议、审批与回传；
- Agent 超时、失败和无模型 fallback；
- 每回合 Agent 激活预算，非相关角色不调用；
- 人格、当前情绪、关系和目标参与提示词合成；
- 所有互动进入游戏复盘投影。

页面验收：

- 玩家能看见任务交给了谁、当前进行到哪一步；
- 能展开 A→B→C 的真实消息和结果；
- 角色不知道的秘密不会出现在其回复中；
- Agent 失败时游戏仍可继续；
- 角色说“已完成”但后台无证据时不会进入正式结算。

退出标准：至少完成调查、跨角色咨询、会议和审批四条真实链路。

## 阶段 D4：五事件与危机链内容

目标：形成一局有起承转合、不是聊天合集的体验。

任务：

- 完成五个主事件的结构化定义和叙事文本；
- 两条跨回合危机恶化链；
- 人物私有目标、秘密和冲突立场；
- 事件的公开/私密反馈；
- 四个结局和结局卡内容；
- 导演的事件候选、节奏和重复抑制规则；
- 单事件测试 fixture 和整局黄金路径。

页面验收：

- 不同处理方式在后续回合产生明显不同结果；
- 同一事件至少支持三种不同类型的自然语言策略，而不是三个文案近似选项；
- 危机不是一次扣分，而会在到期后升级；
- 董事会对手会利用玩家留下的实际弱点。

退出标准：内部试玩三次能得到至少三种不同过程，且因果均可解释。

## 阶段 D4.5：视听表现底座与 Demo 资产包

目标：证明美术、音乐和音效可以由事件与人物状态稳定驱动，同时不和 Game Core 耦合。

系统任务：

- Asset Catalog、Asset Manifest、主题包和版本绑定；
- Domain Event → PresentationPlan 投影；
- Cue 队列、跳过、重播、fallback 和来源追踪；
- 音乐状态机、环境音、SFX、混音和音量设置；
- 图片多尺寸、预加载、缓存、CDN 和低带宽降级；
- 角色表情/姿态标签映射；
- 字幕、减少动态效果和纯文字模式；
- 资源版权、作者、生成来源和审核状态记录。

Demo 最小资产范围：

| 资产 | 数量建议 | 说明 |
|---|---:|---|
| 主视觉与开局封面 | 1 | 建立产品第一印象 |
| 角色基础半身像 | 5 | 五个核心角色 |
| 角色表情变体 | 每人 3 个 | 中性、压力、对抗；共 15 个，不追求全动画 |
| 场景背景 | 4 | 办公室、董事会、私人会面、新闻/监管场景 |
| 主事件关键图 | 5 | 每个主事件一张，可与背景组合 |
| 结局卡图 | 4 | 四个首版结局 |
| 指标/危机/行动图标 | 约 20 | 使用统一图标语言 |
| 音乐 | 4 首/层 | 平静、紧张、危机、结局 |
| 环境音 | 3 组 | 办公室、会议、媒体/城市 |
| 音效 | 8–12 个 | 通知、证据、危机升级、数值变化、结局等 |
| 配音 | 暂不全量 | 只为开场、危机爆发和结局各做少量关键句，亦可全部字幕降级 |

页面验收：

- 同一正式事件能够稳定触发正确背景、人物、表情、音乐和音效；
- 危机升级时音乐平滑提高强度，不重新从头乱播；
- 玩家关闭声音、动画或切换低带宽后仍可完整游玩；
- 任意资源加载失败都有 fallback，不阻塞回合；
- 替换整个主题包后不修改 Game Core 和事件规则；
- 点击表现记录可以查到其来源 Domain Event 和资源版本。

退出标准：五个事件和四个结局均拥有完整 Cue Sheet；PC/移动端和静音/低带宽模式通过验收。

## 阶段 D5：独立玩家产品页

目标：产品经理和普通玩家无需进入 Hub 后台。

页面：

- `/game/speeding`：开局/继续游戏；
- `/game/speeding/:id`：局势、人物、自然语言输入、行动进度；
- `/game/speeding/:id/history`：事件、Agent 互动、状态变化和因果复盘；
- `/game/speeding/:id/ending`：结局卡、指标和关键决定。

任务：

- PC 与移动端响应式布局；
- 回合等待过程提示和异步结果刷新；
- 指标变化、危机钟、人物态度和当前目标；
- 长文本折叠、关键变化突出、技术细节二级展开；
- 建议行动、输入历史和快捷命令；
- 断线恢复和重复提交保护。
- 场景背景、角色站位/表情、关键事件图和结局卡渲染；
- 音乐、环境音、SFX、少量配音及独立音量控制；
- 资源预加载状态、失败降级和低带宽模式。

页面验收：

- 手机和常见 PC 宽度均不横向溢出；
- 玩家清楚知道系统正在咨询谁、等待什么；
- 一局中不会看到 MCP、ToolResult、Schema 等工程词；
- 刷新页面后继续当前回合，不重复扣款或触发事件。

## 阶段 D6：First Playable 测试、部署与底层收口

目标：确认底层机制和五事件内容包可以稳定在线运行，并冻结经过真实试玩验证的 Content Schema v1。此阶段不以交付完整可视化内容工作台为目标。

任务：

- 内容包 CLI/API 校验器和稳定 ID 引用；
- 开发者级单事件沙盒与状态注入；
- Draft → Validate → Test → Package → Publish 的底层接口；
- 游戏局绑定不可变 bundle hash；
- 内容 lint：断链、不可达、非法字段、越界、无结局；
- 一键本地验收和服务器部署检查；
- 冒烟测试、回归测试、成本与延迟报告。

产品验收：

- 研发通过配置修改一个事件的文案、条件或数值并重新打包，产品经理在游戏页试玩结果；
- 修改不会影响正在进行的旧局；
- 发布失败时校验报告给出可定位原因；
- 线上可以新开、游玩、刷新恢复并完成一局。

退出标准：Game Kernel v0、Content Schema v1 和 Speeding Demo Bundle v1 冻结；五事件内容无专用硬编码；线上完成一局。

## 阶段 D7：傻瓜式 Content Studio（First Playable 之后）

目标：在已经被 Demo 验证稳定的 Schema v1 上，把研发配置流程变成产品/策划可使用的“填空式”制作流程。

任务：

- 分步骤世界、角色、指标、事件、危机、结局和视听资源向导；
- GDevelop 式条件/效果表单；
- Twine 式只读关系图，成熟后再开放安全连线；
- 单事件可视化沙盒、条件解释和 state diff；
- 素材库、Cue Sheet、缺失资源和版权检查；
- Draft → Validate → Test → Review → Publish → Rollback 页面；
- 由 Schema/Registry 自动生成表单，新动作和效果不手写页面；
- AI 只生成待审核内容草稿。

页面验收：

- 非研发人员能新建一个不属于五事件 Demo 的事件；
- 能绑定已有角色、规则、危机和美术音乐；
- 能从页面试玩、修正、发布；
- 发布过程不要求修改代码或直接操作数据库；
- 旧局继续使用旧 bundle，新局选择新 bundle。

退出标准：产品经理独立完成一个新事件从创建到线上新局验证；整个过程研发只处理产品缺陷，不编写该事件代码。

## 6.1 每阶段统一“可扩展性门禁”

除各阶段的产品验收外，每个统一版本还必须通过以下检查：

| 门禁 | 最低要求 |
|---|---|
| 无领域硬编码 | 通用模块内搜索不到具体角色、事件和 Speeding 指标名 |
| 协议验证 | API、事件、Action、Effect 和内容包均通过 Schema 校验 |
| 向后兼容 | 上一版本创建的存档可以恢复或至少完整只读回放 |
| 固定重放 | 相同版本、seed 和 Command 得到相同正式结果 |
| 幂等 | 重复请求、重试和刷新不会重复扣款或重复触发事件 |
| 迁移演练 | 在带旧数据的副本上完成升级和必要回滚 |
| 扩展验证 | 用第二个非 Speeding 小样例注册一项指标、动作和事件，不改 Core 代码 |
| 容量验证 | 目标并发下队列、数据库、模型预算和延迟不越过本版本阈值 |
| 故障恢复 | 模型超时、Agent 失败、服务重启后当前局可以继续或明确降级 |
| 安全隔离 | 不同租户、游戏、角色可见信息和扩展权限不串联 |
| 可观测性 | 任一失败能通过 trace 定位到阶段、版本、规则和外部依赖 |
| 响应式 | PC 与移动端使用同一业务投影，核心流程均可完成 |
| 媒体兼容 | 旧内容引用的资源版本仍可访问；资源失败可降级且不影响结算 |
| 版权来源 | 上线资源具备作者、许可证/授权、生成来源和允许使用范围 |

“第二个非 Speeding 小样例”不需要成为完整游戏，只需使用完全不同的领域词，例如餐厅经营：新增 `库存` 指标、`采购` 动作和 `供应中断` 事件。如果必须修改 Game Core 才能注册，说明扩展协议不合格。

## 6.2 Demo 阶段的容量目标

首版先建立可测量基线，不追求虚假大规模：

- 单实例至少承载 50 个同时活跃游戏会话；
- 每局最多 5 个 Agent，但每回合默认激活不超过 2 个，会议除外；
- 普通页面读取不触发模型调用；
- 每条玩家 Command 只允许一个正在提交的权威结算；
- 模型/Agent 操作超时后 30 秒内显示降级状态，不无限等待；
- 服务重启后恢复所有已确认但未完成的 Command；
- 事件与状态查询采用分页，不随游戏长度一次返回全部历史；
- 存档快照和事件日志分别设定保留、归档和恢复策略。

后续扩容通过增加 worker、队列分区、只读投影和存储归档实现，不改变玩家 Command 与 Domain Event 协议。

## 7. 验收用例

### 用例 A：复合自然语言行动

玩家输入：

> 暂停出售，先让财务核查付款路径，让法务看监管风险；消息只在我们三人之间，明晚前给我结果。

通过标准：拆成暂停、委派、咨询、保密和期限；确认后才执行；两条任务可查询并回传。

### 用例 B：不服从与冲突

玩家要求法务隐瞒证据。

通过标准：法务根据人格和职责可以拒绝、附条件接受或私下留档；Game Core 判定实际行动和风险，不由角色一句话决定。

### 用例 C：后台串联

财务发现异常后主动咨询法务，法务再向董事会对手泄露部分信息。

通过标准：玩家未必立即知道，但后台存在完整 A→B→C 证据；相关人物 Observation 随传播更新。

### 用例 D：危机跨回合

玩家只处理舆情而忽略付款期限。

通过标准：短期声誉改善，但流动性钟继续推进并在到期后触发更严重事件。

### 用例 E：重放与结局

以相同 seed 和相同行动重跑。

通过标准：正式数值、事件抽样和结局一致；AI 文案允许措辞不同，但不得改变事实。

## 8. 风险与控制

| 风险 | 控制方案 |
|---|---|
| 模型编造已执行行动 | 只有 ToolResult/正式事件可进入世界状态 |
| 自然语言误解 | ActionPlan 预览、置信度、歧义确认 |
| Agent 响应慢 | 过程提示、异步 callback、deadline 和 fallback |
| Token 成本失控 | 每回合激活上限、角色 LOD、模型档位和预算 |
| 故事散掉 | 五个已发布事件、危机钟、导演只选合法候选 |
| 数值不可解释 | typed effects、规则解释树、before/after diff |
| 内容修改破坏旧局 | 不可变 bundle hash 和内容版本绑定 |
| 又和 Hub 耦合 | 所有 Speeding 名词只存在能力包/Game Core/玩家应用 |
| 移动端失控 | D0 原型和 D5 同时验收 PC/移动端 |
| 部署反复失败 | 单一部署脚本、健康检查、数据库迁移和回滚说明 |

## 9. 开发组织建议

每个阶段作为一个统一版本提交，采用当前约定的协作模式：

- 主 Agent：拆解、接口冻结、集成、统一测试和部署；
- 子 Agent A：Game Core/规则；
- 子 Agent B：玩家前端与响应式；
- 子 Agent C：内容、测试 fixture 和复盘；
- 产品经理：只验收统一版本页面，不逐个验收子任务。

阶段内可以并行，但必须先冻结共享 Schema；任何子 Agent 不得自行增加世界字段、动作类型或绕过 ToolResult 写状态。

## 10. 建议决策门

审核本计划时只需确认五件事：

1. Demo 主题是否采用“资产出售 + 私事曝光 + 政治交易 + 监管 + 夺权”；
2. 5 个角色是否足够，是否要替换某个角色；
3. 8 个指标和 3 个危机钟是否符合产品方向；
4. 首版四个结局是否合理；
5. 是否批准按 D0 → D6 完成底层与 First Playable，并在 Schema v1 稳定后另行批准 D7 Content Studio。

建议不调整技术主线：先 D0 协议与原型冻结，再 D1 确定性核心；不要先堆事件，也不要在 Schema 未经试玩验证前制作完整内容编辑器。
